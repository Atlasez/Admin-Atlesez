# 運営メンバー受入・実運用への準備

更新日: 2026-10-05。対象は `admin.atlasez.org` / Worker `atlasez-admin`。

この文書は、実装済みの入口と、人数を増やす前に解決する課題を記録する。
今回の作業では実在の人への招待、アカウント作成、本番データ・権限の変更、通知送信は行っていない。
修正の本番反映と一般メンバーでの確認が終わるまでは、実運用可能と判定しない。

## 現在利用する仕組み

- Googleログイン、応募基本情報、プロジェクト別応募、本人の応募状況確認。
- 応募管理の受入処理。応募状態、プロフィール、所属、状態変更記録を一括保存する。
- 基本プロフィールとプロジェクト内自己紹介の初回入力。
- メンバー用ポータル、タスク、タスク詳細の作業メモ、カレンダー、マイページ。
- 参加後の案内とタスクテンプレート。テンプレートの保存と実タスク作成は別操作。
- Atlasメンバーのアーカイブ・復元、権限変更履歴、操作履歴。

入口があることと、通常メンバー・プロジェクト責任者が一連の操作を完了できることは、別々に確認する。
受入処理のメール・Discord連携は設定状態を確認し、不要な送信を避けるため、本番で試験登録を繰り返さない。

## この変更で扱うアクセス問題

従来の `getUserStageForEmail()` は最新応募の状態からアクセス段階を決めていた。
そのため、参加中の人が別プロジェクトへ応募すると、元の所属が残っていても応募者扱いになり、メンバー用画面へ入れなくなる。
管理側で直接所属を登録した人も、受入済み応募がないと参加後の入力へ進めない。

修正では、有効な所属をメンバーアクセスの根拠として扱う。基本プロフィールと所属先の自己紹介が未完了なら入力へ案内し、完了済みの所属があれば追加応募中も既存の活動を継続できるようにする。
過去の受入済み応募だけで、所属を失った人を再有効化しない。Atlasのアーカイブ済み状態を尊重し、他プロジェクトの有効な所属は維持する。

検証には、二つ目の応募、応募履歴のない直接登録、所属削除後の古い受入済み応募、Atlasアーカイブと別プロジェクト所属の併存を含める。
実装・隔離環境の検証と、本番確認の完了状態はPR・作業記録に残す。

2026-10-05のローカル検証は単体430件、E2E357件が成功。E2E14件は実本番スモークなどの条件付き検証のためskipしており、本番の認証・データ・メール／Discord接続を確認した結果ではない。
deploy-config、型検査、lint、format、ADMIN build、build-info、差分検査も成功。管理者のプロフィール権限表示が維持されることも回帰検証に含めた。

## 受入を広げる前に対応する課題

| 優先 | 課題と確認根拠                                                                                                                                     | 必要な対応                                                                                                                                                                |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 高   | 所属のmanagerだけでは応募管理・自己紹介承認へ入れない。`getProjectReviewerScope()` と共通管理APIゲートが、先にAtlas用の管理scopeを要求する。       | プロジェクト責任者を対象プロジェクトの所属・roleで認可する。所属外プロジェクトとAtlas記事へのアクセスは付与しない。                                                       |
| 高   | 全分野権限 `*` の取消後も、Atlasのmanager所属が残る。`atlasMembershipStatement()` は `INSERT OR IGNORE`、権限削除APIは所属roleを更新しない。       | 自動付与したmanagerと独立に任命したmanagerを区別できるようにし、取消結果を表示・監査する。既存データには付与元がないため、managerを一律に降格せず、現在の任命を確認する。 |
| 高   | Atlasアーカイブ後の再受入経路も確認が必要。`updateApplication()` の受入処理は所属を追加するため、古い応募から再追加できない境界が必要。            | Atlas受入時にアーカイブ状態を確認し、復元前の再付与を拒否する。他プロジェクトの受入は、そのプロジェクトの権限と所属で判断する。                                           |
| 中   | 一般メンバーのプロジェクト内自己紹介更新と紹介一覧は `getAdminScope()` を要求し、メンバー用API許可対象にない。                                     | 本人の変更申請・所属先の紹介閲覧を、メンバーscopeとプロジェクト所属で許可する。承認操作は責任者へ限定する。                                                               |
| 中   | 活動休止・退会は `memberProcedureRequests()` の本人履歴取得・pending保存だけ。管理側の一覧・処理経路がなく、一般メンバーにも申請画面が閉じている。 | 本人申請、担当者確認、引継ぎ確認、承認・却下、所属・権限停止、再開・復元を一連の手順として実装する。予定日だけで処理済みと表示しない。                                    |
| 中   | 参加後の案内はあるが、受入担当者・最初のタスク・確認担当者の割当と初回フォロー完了を追跡する仕組みがない。                                         | 受入一覧に担当者、初回タスク、確認担当者、相談先、初回フォロー予定・実施日を持たせ、未設定を検出する。                                                                    |

コード根拠は `src/admin-worker.ts` の各関数、アクセス段階は `src/lib/user-stage.ts`、参加案内は `src/pages/admin/getting-started.astro` を参照する。
既存テストには権限境界・アーカイブ／復元の確認があるが、上記の複数応募・managerの付与元・一般メンバー手続きを同時に確認する必要がある。

## 少人数での運用開始手順

1. 受入担当者、各プロジェクト責任者、問い合わせ先を決める。
2. 隔離環境で、新規参加者、既存参加者の追加応募、プロジェクト責任者、担当外ユーザー、退会済みユーザーを確認する。
3. 本番へ配信されたSHAと対象Workerを確認し、一般メンバーと責任者の認証済み画面で主要操作を確認する。
4. 実際の受入時に、所属・初回入力・最初のタスク・確認担当者・相談先を確認する。
5. 最初のタスク完了後に担当者が困りごとと作業量を確認し、その結果と次の担当を記録する。
6. 休止・退会時は未完了タスク、原稿、予定、通知先の引継ぎを確認してから所属・権限を変更する。

## 本番反映の停止条件

今回の確認ではGitHub mainと公開 `build-info.json` の配信SHAが一致していないため、mainの内容を本番で確認済みとは扱わない。
また、ユーザーから提示されたルールは「Workers Buildsのみ」、最新main内の運用文書は「GitHub Actions deploy workflowのみ」で、配信経路の指示に相違がある。
ユーザーの提示した指示を優先し、この相違を解消して正規経路を確定するまでは配信しない。経路の整理は、設定値・影響・復旧方法を含むレビュー対象とする。

CI成功、レビュー完了、正規経路の確定、対象main SHAの配信、Worker Versionの100%配信、認証済みChrome確認が揃うまで、本番反映・実運用準備完了とは記録しない。
停止理由と進捗はPRおよび作業記録に残し、本番データを直接変更して配信の不足を補わない。
