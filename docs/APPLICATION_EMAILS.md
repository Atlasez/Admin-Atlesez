# 応募メール通知の設定

応募を受け付けると、次の処理が行われます。応募が連続して届いた場合も、応募1件ごとに別の対応タスクとメール配信キューを作成します。

- 応募者へ受付確認メールを送る
- 運営内運営へ新着応募メールを送る
- 運営事務局プロジェクトに「応募対応」タスクを作る
- 管理画面の通知ベルに新着応募を表示する

応募データの保存、対応タスク、管理画面通知はメール設定がなくても動作します。メールはResendの配信キューに入り、送信失敗時は最大5回まで再試行します。配信は同時起動時の重複送信を防ぎながら、1回最大100件ずつ処理します。

同じ学校・職場などで同じネットワークから応募が集中する場合に備え、同一IPの制限は認証済み応募50件／10分、公開取込20件／10分に分けています。同じメールアドレスの応募が確認中の場合だけは、二重応募として受け付けません。

## 送信元アドレス

送信元には、Resendで認証した `atlasez.org` のアドレスを使います。例：

```text
Atlasez運営 <no-reply@atlasez.org>
```

Resendでドメインを追加し、表示されたSPF・DKIMなどのDNSレコードを `atlasez.org` に登録してから設定してください。Gmailの個人アドレスをそのまま送信元にするのではなく、運営ドメインの専用アドレスを推奨します。

## Cloudflareへの設定

管理WorkerにResendのAPIキーと送信元を登録します。APIキーは秘密情報なので、リポジトリや `wrangler.admin.jsonc` には書きません。

```bash
npx wrangler secret put RESEND_API_KEY --config wrangler.admin.jsonc
npx wrangler secret put EMAIL_FROM --config wrangler.admin.jsonc
```

通常は運営内運営のメールアドレスをD1の権限表から自動取得します。臨時に固定の追加宛先を指定する場合だけ、次を設定します。

```bash
npx wrangler secret put APPLICATION_OPERATIONS_EMAILS --config wrangler.admin.jsonc
```

複数の宛先はカンマ区切りで入力できます。送信元や宛先を変更した後は、管理Workerを再デプロイしてください。

## 配信状態の確認と失敗時の対応

応募担当者は、担当プロジェクトの[応募管理](https://admin.atlasez.org/admin/applications/)で応募を開き、「メール処理状況」を確認します。この欄には種別・状態・試行回数・次回試行予定・更新時刻を表示し、宛先、件名、本文は表示しません。プロジェクト責任者は自分の担当プロジェクトに属する応募の状態だけを確認できます。

- **Resend受付済み**は、送信APIが要求を受け付けたことを示します。応募者の受信箱へ届いたことは示しません。Resendの履歴で最終イベント（配信、バウンス等）を確認します。
- **送信待ち / 自動再試行待ち / 送信処理中**は、次のCron処理を待ちます。応募自体と管理画面通知はメール配信とは別に確認します。
- **要確認**は、宛先不正、試行上限、送信結果不明、またはResendの冪等性キー保持期間を過ぎた可能性があります。特に結果不明・期限切れは自動再送されません。

失敗や長時間変化しない状態を見つけたら、担当者は応募のメール種別・状態更新時刻・試行回数・エラー分類を記録し、Resendの管理画面で承認済み送信元、宛先（応募者宛の場合）、時刻、件名、最終イベントを照合します。Resend側で送信済み・配信済み・処理中と確認できる場合は再送しません。結果が見つからない、または曖昧な場合も重複防止のため再送を止め、Resendアカウント管理者へ照会します。

Resendが送信を受け付けていないと明確に確認できた場合に限り、運営のメール送信方針に従って担当者が個別連絡します。送信前に正しい宛先と連絡内容を応募レコードで確認し、実送信後は担当タスクの「引き継ぎ履歴」に、実施者、時刻、メール種別、Resend側で確認した結果を記録します。本文や不要な個人情報を履歴へ複写しません。配信キューのD1行を直接編集・削除したり、失敗行をSQLでpendingに戻したりしません。

現在、ADMINはResendのメールIDを配信行へ保存せず、失敗メールを画面から再送・手動解決済みにする機能もありません。そのため、Resend履歴で送信を確定できない場合は、自動・手動とも再送せず、運営責任者へエスカレーションします。将来、プロバイダー照合IDを保存して運営が状態を記録する機能を追加する場合は、D1 migrationのバックアップ・レビュー・適用手順を別途計画します。
