## 第1部 学習サイト「アトラス」

### 1. すでに持っているのに画面に出していないデータを出す（S・効果大）

`src/content.config.ts` の記事スキーマには次が**必須項目として全164記事に入っています**が、
`src/lib/i18n.ts` にラベルがあるだけで、**どのページにも表示されていません**。

| 項目               | 内容                                           | 対応           |
| ------------------ | ---------------------------------------------- | -------------- |
| `difficulty`       | introductory / basic / intermediate / advanced | **表示しない** |
| `estimatedMinutes` | 読了目安（分）                                 | **表示しない** |
| `reviewers`        | 査読者                                         | **表示しない** |

### 取り下げの経緯

一度は記事ヘッダと記事カードに「難易度: 標準」「推定学習時間: 45分」を出し、学習サイトHomeの
総合リストにも所要時間を添えましたが、**運営判断で撤去しました**（共通部品
`ArticleMeta.astro` ごと削除）。

再検討するなら、先に下記「難易度フィルタを見送った理由」のデータ問題を解く必要があります。
難易度が実質カテゴリごとの定数になっている状態では、表示しても読者の判断材料になりません。

### 査読者を表示しなかった理由

`reviewers` の実データを確認したところ、`src/content/articles/jpn/physics/overview/what-is-physics.md`
に **個人のメールアドレスがそのまま入っていました**（もう1件は `example-reviewer` というプレースホルダ）。
このまま画面に出すと、公開サイトにメールアドレスを掲載することになります。

表示する前に、次のどちらかを決める必要があります。

- 表示名（`atlas-physics-team` のような内部ID、または本名）に置き換える
- 査読者は画面に出さない方針を明文化する

なお、このメールアドレスは**公開リポジトリ `Atlasez01` にも入っています**。運営として問題なければ
そのままで構いませんが、意図しない掲載なら差し替えを検討してください。

読者が記事一覧を見たときに一番知りたいのは「自分に読めるか」「どれくらいかかるか」です。
データはもう揃っているので、**表示するだけ**で体験が変わります。

実装したもの:

- 共通部品 `src/components/ArticleMeta.astro`（「難易度: 基礎」「推定学習時間: 12分」）
- 記事ページのヘッダ（`[category]/[slug].astro`）
- カテゴリページの記事カード（`[category]/index.astro`）
- 学習サイトHomeの総合リストには所要時間だけを添えた（`[locale]/index.astro`）。
  ここは行が密なので、難易度バッジまで出すと読みにくくなるため

### 難易度フィルタを見送った理由

**いまのデータでは絞り込みが成立しません。** 全31カテゴリを調べたところ、
**難易度が2種類以上あるカテゴリは0件**でした。

| 分野        | 難易度の内訳                     |
| ----------- | -------------------------------- |
| mathematics | introductory 1 / intermediate 37 |
| kanji       | introductory 1 / basic 86        |
| chemistry   | introductory 1 / basic 17        |
| physics     | basic 1 / intermediate 9         |

分野単位で見ても「総論記事1本 + 残り全部同じ難易度」で、`advanced` は1件も使われていません。
つまり `difficulty` は実質「カテゴリごとの定数」になっており、絞り込みの軸になりません。

フィルタを入れるより先に、**記事を書くときに難易度を実態に合わせて付ける**運用が要ります。
[ADDING_ARTICLES.md](ADDING_ARTICLES.md) に難易度の判断基準（前提知識をどこまで仮定するか）を
書き足すのが最初の一歩です。それができてから、フィルタと学習地図の塗り分けを入れると効きます。

### 2. 学習記録の端末間引き継ぎ（M・BACKLOG #2 への回答）

いま学習記録は `localStorage` だけで、書き出し・読み込み（JSON）は実装済みです。
`docs/BACKLOG.md` は「同期が要るならログイン導入が前提」としていますが、
**ログインなしで9割の需要を満たす方法**があります。

**引き継ぎコード方式**

1. 端末Aで「引き継ぎコードを発行」→ 学習記録のJSONを学習サイトWorkerへPOST
2. Workerは6〜8桁のコードを発行し、D1に**24時間だけ**保存（記録の中身は記事IDと段階のみ）
3. 端末Bでコードを入力すると取得してマージ、取得後は即削除

- アカウント・メールアドレス・Cookie が要らないので、いまの匿名方針をまったく崩しません
- 期限切れの掃除は既存の `purgeExpiredPersonalData` と同じ形で cron に足すだけ
- 実装: `migrations/00XX_learning_transfer_codes.sql`、`src/worker.ts` に2エンドポイント、
  `src/components/A11ySettings.astro`（表示設定メニュー）にUI

将来、読者ログインを入れることになっても、この仕組みはそのまま「移行の入口」として使えます。

### 3. 復習キュー（M・再訪の動機をつくる）

`src/lib/history.ts` は「読んだ → 理解した」の2段階を持ち、段階を増やすのも
配列に足すだけという作りになっています。ここに**間隔反復**を乗せられます。

- 「理解した」を付けた日を記録し、1日後・1週間後・1か月後に「復習しませんか」と出す
- 学習サイトHome に「今日の復習（3件）」を置く
- すべて `localStorage` の中だけで完結し、サーバもアカウントも不要

学習サイトは「調べにくる場所」から「通う場所」に変わります。新規記事の追加ペースに
依存せず再訪が生まれるので、記事数が伸び悩む時期の支えになります。

### 4. 学習地図を「いまいる場所」から描く（M・BACKLOG #4 #5 への回答）

現状は全体像から入るため、初見の負荷が高く、トップページのHTMLも 180KB あります
（BACKLOG には 128KB とありますが、いまは 180KB です）。

- 記事ページから地図へ飛んだときは、**その概念を中心に2ホップだけ**描く。
  「全体を見る」は明示的なボタンにする
- 経路検索の選択肢（161項目×2）とオートコンプリート候補をHTMLから外し、
  すでに別ファイルになっている `graph.json`（90KB）から組み立てる
- JavaScript が無い環境向けに、地図の下へ「前提 → この概念 → 次に学ぶ」の
  簡素な3列テーブルを置く（`graph.json` を使わずビルド時に出力できる）

3つ目は、検索エンジンに概念の関係が読めるようになるという副次効果もあります。

### 5. 数式の重い記事を軽くする（M）

MathJax のSVGをビルド時に本文へ埋め込んでいるため、数式の多い記事が肥大化しています。

| ページ                                        | HTML  | gzip | `mjx-container` |
| --------------------------------------------- | ----- | ---- | --------------- |
| `atlas/ja/mathematics/module-theory/modules/` | 1.2MB | 99KB | 569個           |

500KB超が16ページ、200KB超が37ページ（全255ページ中）。転送量はgzipで収まりますが、
DOMノード数由来のパース・レイアウト負荷は残るため、低スペック端末の初期表示に効きます。

- 折りたたみの中（`<details>` に変換済みの証明など）の数式は、開いたときに描く
- あるいは数式が一定数を超える記事だけ CHTML 出力に切り替える（フォント読み込みと引き換え）

### 6. 「書き手募集」を学習サイトから直結させる（S・効果大）

いま `src/data/planned-articles.json` を使って「本文準備中」を38件表示していますが、
**そこで行き止まり**です。ここに一行足すだけで、読者が書き手になる導線ができます。

**実装済み。** 次の2か所に導線を置きました。

- カテゴリページの準備中カード → 「この記事を書いてみませんか」
- 学習サイトHomeの総合リストの準備中項目 → 「書いてみませんか」

リンク先は `applyUrl("?project=atlas&subject=<分野>&article=<記事名>")` で、
応募フォーム側で **希望分野のチェックを自動で入れ、「書きたい記事」欄に記事名を埋めます**
（`src/pages/apply/index.astro`）。応募者は空欄を埋め直す必要がありません。

補足: これを入れる前は、`join.astro` が渡していた `?project=` を応募フォームが**まったく読んでおらず**、
クエリは捨てられていました。今回 `subject` と `article` の読み取りを足しましたが、
`project`（どのプロジェクトへの応募か）はフォームにもAPIにも受け皿がないままです。
プロジェクト別に応募を仕分けたいなら、`submitMemberApplication` に項目を足す必要があります。

### 7. 検索の表記ゆれ対策 — 訂正: すでに実装済みでした

当初「未対応」と書きましたが、調べ直したところ**すでに実装されています**。
`[category]/[slug].astro` の `data-pagefind-body` の中に `.visually-hidden` の
メタデータ領域があり、`aliases`・`tags`・概念IDがすべて出力済みです。誤りでした。

残っている改善余地があるとすれば、Pagefind が日本語のステミングに対応していない点そのもの
（ビルド時に警告が出ます）ですが、これはPagefind側の制約で、`aliases` を充実させる以外に
リポジトリ側でできることはあまりありません。

### 8. 記事末尾の導線 — 訂正: すでに実装済みでした

当初「未実装」と書きましたが、こちらも**すでに揃っています**。誤りでした。

- 「次に学ぶ」: `content.ts` の `nextArticles()` が `recommendedNext` から導出し、
  記事ページの `<aside>` に「前提記事 / 次に学ぶ / 関連記事」として出ています
- 「理解した」ボタン: `HistoryStageControl` が記事の上下2か所にあり、E2Eでも同期を検証済み
- 問題報告フォーム: 記事末尾に設置済み

強いて挙げるなら、`<aside>` は画面幅の広いときサイドバーに出るため、
**本文を読み終えた位置に「次に学ぶ」が見えない**ことです。PCで読み終わった読者の視線は
本文の下端にあるので、本文末尾にも同じ導線を置くと効く可能性があります。
ただし重複表示になるので、入れるならA/Bで確かめてからが安全です。

## 第2部 運営サイト（メンバー用サイト・学習サイト運営）

### 9. プロジェクトを動的ルートにする（M・現在は潜在的な404）

`POST /api/admin/projects` は任意のslugでプロジェクトを作れますが、

- `src/pages/admin/projects/[slug]/workspace.astro` の `getStaticPaths()` は3件固定
- プロジェクトのトップは `secretariat.astro` / `seminar-platform.astro` の個別ファイル
- `src/admin-worker.ts` のページ許可リストも3プロジェクト分をベタ書き

このため4つ目を作ると、**メンバー用Homeにカードは出るがクリックすると404**になります。

- プロジェクトのトップとマイページを `[slug]` の動的ルート1本に統合する
- 許可リストを `^/admin/projects/[a-z0-9-]{2,60}/(workspace/)?$` の正規表現に置き換える
- プロジェクト名・説明はビルド時ではなくAPIから取得する（`getStaticPaths` はD1を見られないため）

いま3プロジェクトだから困っていないだけで、増やした瞬間に壊れます。増やす前に直すのが安いです。

### 10. 記事改善の優先順位が分かる統計にする（S・効果大）

`listArticleAnalytics`（`src/admin-worker.ts`）は `ORDER BY completed_reads DESC`、
つまり**よく読まれた記事**を上から並べています。しかし運営が知りたいのは
**直すべき記事**です。

**実装済み。** 次を入れました。

- API に `?sort=needs-work` を追加。閲覧が5件以上ある記事のうち**完読率の低い順**に並べます
  （分母が小さいと率が暴れるので、閲覧数のしきい値を先に効かせています）
- 応答に `completion_rate` / `engagement_rate` / `report_count` を追加
- 画面に「完読率」「報告」の列と、「よく読まれた順 / 直す価値が高い順」の切り替えを追加
- 完読率が30%を下回る記事には「要改善」を添える（色だけに頼らない）

**残り:** この表から `/admin/editor/` の該当原稿へ1クリックで飛べるようにすると、
「気づく → 直す」が途切れません。原稿と記事の対応付け（`editorial_documents` と `article_id`）を
たどる必要があるので、次の作業に回しました。

### 11. 査読の滞留を見えるようにする（M）

`listEditorialReviewRequests` と `editorial_review_assignments`、`editorial_review_due_dates`
はすでにあります。運営でいちばん詰まりやすいのは査読なので、ここを可視化する価値が高いです。

- 査読待ちの**日数**でソート（いま何日止まっているか）
- 査読者ごとの同時担当数。偏っていたら割り当て時に警告する
- 「下書き → 査読依頼 → 査読完了 → 公開」の各段階の中央値リードタイム
  （`editorial_revisions` と `editorial_publication_status` から出せます）

数字を出すと「誰が遅い」ではなく「どこで詰まる」が見えるので、運営の会話が変わります。

### 12. 週次ダイジェスト（S）

管理Workerの cron は毎日3時（UTC）に動いています（`wrangler.admin.jsonc`）。
Discord webhook も Resend も配線済みなので、週1回の要約を流すのは低コストです。

- 今週公開された記事 / 査読待ちの件数と最長滞留日数 / 新しい問題報告 / 期限切れのToDo
- 宛先は既存の Discord チャンネルと `APPLICATION_NOTIFICATION_EMAIL`

運営サイトを毎日見にいく人は多くありません。**向こうから届く**形にすると、
滞留がそもそも起きにくくなります。

### 13. 学校名の候補を検索APIにする（M・今回の応急処置の恒久策）

今回は「学校名欄に触れるまで読み込まない」形に直しましたが、触れた人は
やはり 3.8MB・6万件を受け取ります。

- 管理Workerに `GET /api/public/institutions?q=...` を作り、前方一致・部分一致の
  上位30件だけ返す（D1に取り込むか、KVに頭2文字ごとの分割JSONを置く）
- 生成データに**文字化けが9件**あります（`?町学園女子高等学校`、`開志創造?学` など）。
  `scripts/build-institution-directory.mjs` の文字コード処理を直し、再生成してください

### 14. テストの薄いところを埋める（M）

`src/admin-worker.ts` は5,940行あり、権限判定・査読フロー・Discord同期・公開処理を
担っていますが、Vitest の対象になっていません（単体テストは今回追加した分を含めて34件）。
E2E 41件は公開サイトだけを見ています。

優先して回帰テストが欲しいところ:

- `getAdminScope` の権限境界（`*` を持つ人と担当分野だけの人）
- `adminReturnPath` のホワイトリスト（オープンリダイレクトの防止）
- `isSameOrigin`
- `purgeExpiredPersonalData` の保持期間

Worker の関数は素のTypeScriptなので、D1をモックすれば Vitest でそのまま動きます。

### 15. 匿名統計APIの保護（S）

`/api/article-analytics`（`src/worker.ts`）にはレート制限も重複排除も、記事の実在確認も
ありません。閲覧数は誰でも水増しでき、存在しない記事IDの行を任意のタイトルで作れます
（表示側は `escapeHtml` を通しているのでXSSには至りません）。

- 記事報告と同じ `reporter_hash` ベースの上限を入れる
- `article_id` をビルド時に生成した既知IDの集合と突き合わせる
