## 日次運用チェックリスト（主担当・代理の指名後に使用）

### 応募を受け取る

1. 運営画面の応募一覧で未対応queueを確認し、応募先project、received time、state、最終更新を確認する。
2. project選考権限を持つ主担当へ割り当て、代理担当がいる場合は不在時の引継ぎ先として記録する。応募内容を不要な外部文書・Issue・チャットへ複製しない。
3. 受付通知queueのpending/retry/sending/failed、最古滞留、試行数を確認する。運営画面の「診断正常」だけでメール到達と判定しない。
4. 必須情報不足、重複応募、プロフィールだけ保存された応募、本人からの訂正/削除依頼を区別して本人へ確認する。本人確認方法と担当は運営決定待ち。
5. 判定または次の連絡が完了するまで未対応queueに残し、担当者・次回確認日・現在待っている相手・完了条件を記録する。
6. 受入済み応募の「参加環境」状態と試行数を確認する。Discord同期が終端`failed`なら、Discord担当へ割り当て、本人への最終案内と次回確認期限を記録する。自動メールは初回失敗・成功時だけのため、再試行中や6回到達をメール到達済みと扱わない。

### 選考・面談・受入

1. 応募に対応したprojectのmanager/global権限を持つ人だけが閲覧・判断する。担当外project queryやID直打ちは専用roleアカウントで受入検証する。
2. 応募者へ説明する募集条件、選考段階、必要な追加情報、次回連絡目安を、公開募集ページと一致させる。

5. 見送り時は状態、連絡、応募記録の削除起算、別profileに対する処理を確認する。現在の応募行180日削除がprofile削除を意味しないことを本人説明と運用に反映する。

## 障害・バックアップ・復旧運用

### 通常時のバックアップ準備

1. D1 exportの内容は会員・応募・原稿等の個人情報を含む。承認済み保管先、暗号化、アクセス者、保持/削除、失敗通知を決めるまで自動uploadや外部転送を設定しない。
2. Backupを取る頻度、migration前の取得、exportのCPU/Duration/行数影響、中断条件を計測・決定する。
3. `ADMIN_D1_RECOVERY.md`の過去検証はSQL exportの隔離SQLite整合性検査まで。D1本番への復旧、外部副作用、Cron再実行を含むend-to-end復旧を証明しない。

### 障害時の手順

1. P0候補（権限漏えい、応募停止、個人情報の誤公開、書込整合性崩れ、全体復旧不能）は書込・公開操作を止め、発生時刻、画面/API、SHA、request idだけを記録する。PII本文、token、メール本文は残さない。
2. 主担当は代理と管理者へ合意済み窓口で連絡し、ユーザー影響、範囲、最後に成功した操作、暫定回避を記録する。
3. Cloudflare source/SHA/Version、Worker名、D1 migration状態、Cron個別queue/checkpoint、provider結果を読み取り確認する。Cloudflare Builds障害はIssue #509へ継続記録し、token scopeや配信経路を独自変更しない。
4. Deploy/rollback/route/cache変更、D1 write/migration/restore、実メール/Discord通知は、対象と復旧方法を明記した別の明示承認がない限り行わない。
5. D1復旧時は`ADMIN_D1_RECOVERY.md`をたたき台に、停止対象・bookmark時刻・失われる書込・復旧後の整合確認・再開判定を二人で照合する。現行文書だけで本番restoreを実施できるとは扱わない。
6. 復旧後は対象main SHA、Build run、fixed Worker/Version/100%、build-info、権限別主要画面、queue滞留、D1整合性を記録し、運営代表が再開を判断する。

## Go / No-Go

### 限定運用のGo条件

- Workers Buildsに成功runがあり、checkout/main SHA、固定Worker、100% Version、live build-infoが照合済み。sourceが`wrangler`の現Versionはこの条件を満たさず、Worker build由来が追跡できる。
- D1の現行migration listが記録され、最新backupの保存先・閲覧者・失敗通知が明確。隔離復元演習が実施され、計測値が記録される。
- 応募者プロフィールの保存時点、閲覧者、未完了profile保持、本人削除窓口を決定し、募集ページとprivacyへ明示する。
- 主担当と代理、queue確認頻度、初回連絡目安、事故窓口が指名される。
- 個人データの種類・目的・起算日・保持期間・例外・backup copyの削除を運営/privacy責任者が決定し、公開説明と一致する。承認前は`ADMIN_PERSONAL_DATA_RETENTION_ENABLED`を設定せず、記事報告hash/contactの追加消去を有効化しない。既存の認証session・rate limit・採否確定済み応募の整理は継続する。決定後にだけ隔離境界test、本番設定の別承認、実行記録を行う。公開記事報告のsalt Secretは値を閲覧せず名前と正常応答で確認し、hash/contact期限処理と公開説明を照合する。
- P0 OPS-28の修正がmain/liveへ反映され、専用sandboxで異分野editorの403/本文非包含、担当分野editorと全体adminの正常動作を確認する。

### 2026-10-13 応募メール再試行期限の修正（OPS-31 / P1）

- **現在確認した不具合:** `src/lib/application-email-delivery.ts`はResendの24時間冪等性期間を、応募受付時に作られるキュー行の`created_at`で判定していた。受付からCron初回処理まで長く待った行は、初回provider要求が一時失敗した後、初回要求から24時間以内でも次のCronで`provider_idempotency_window_expired`へ終端化され、自動再試行されない。応募・運営タスクはメールとは別に保存されるが、応募者の受付/案内通知と運営通知が遅れる可能性があるためP1（限定運用の応募記録を失う問題ではないが、一般募集前に修正または担当者が確実に実行できる暫定手順が必要）とする。
- **根本原因と修正:** D1 migration `0132_application_email_first_attempt.sql`で`first_attempt_at`を追加し、既存の試行済み行だけ`created_at`で保守的に補完する。dispatcherはprovider要求直前のclaim時刻を初回時刻として一度だけ保存し、その時刻から24時間以内だけ同じ冪等性キーを再利用する。attempt_count=0の古いpending行はqueue作成からの経過時間で止めず、試行済みで初回時刻が欠落した行は安全側で自動再送しない。Resendの24時間保持仕様は[公式発表](https://resend.com/changelog/idempotency-keys)を参照。
- **隔離再現・回帰:** `.test`宛先とSQLite in-memory fixtureのみで、キュー作成を初回試行の3日前に設定し、初回503、6分後の同一キーでの再試行成功、`first_attempt_at`不変を確認した。migration fixtureでは未試行pending行をNULLのまま保持し、試行済み行を`created_at`へ補完し、両行の状態/件数が保たれることを確認。production D1、Resend実送信、応募実データは使用していない。
- **データ/Worker影響:** additive D1 schema migrationが必要である。PRレビュー、承認済みバックアップ取得と適用前確認、migration実行・結果記録が完了するまで、新dispatcherコードを本番Workerへ反映してはならない。通常Buildがmigrationを適用することはない。適用前には固定D1 migration listとバックアップの最新性を再確認し、Workers Builds復旧後の正規main Build/Version/SHA照合を行う。rollbackはレビュー済みコード変更で行い、追加列をdropしたりD1行を直接書き換えたりしない。
- **状態:** 修正・回帰テストはADMIN PR [#526](https://github.com/Atlasez/Admin-Atlesez/pull/526) branchに追加中。main/live未反映、migration未適用、Workers Builds復旧待ち。PR headとCIの確定結果は次回追補する。
