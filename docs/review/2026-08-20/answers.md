# 2026-08-20 レビュー質問への回答

## Q-R1: リポジトリとデータ保存先の違い

リポジトリは、Webサイトを作るためのソースコード、画面、設定、Markdown原稿、DBマイグレーションの変更履歴をGitで管理する場所です。データ保存先は、公開後に利用者が入力・生成したプロフィール、応募、タスク、コメント、画像などを保存する実行環境です。リポジトリを分けなくても、保存先は用途ごとに分けられます。

本構成では `mitukx/atlasez-admin` の一つのリポジトリに公式・学習・メンバー・各運営画面とWorkerコードを置きます。公開記事は `src/content/articles/`、同梱する小規模な配信用画像は `public/images/`、スキーマ変更は `migrations/` に置きます。運用データはCloudflare D1の `atlasez-reports`、記事編集用画像はD1（公開時に `public/images/editorial/` へ反映）、認証はCloudflare Access、公開原稿の確定版はGitHubへ保存します。

分ける理由は、コードの一貫した変更・レビューを一つのPRで行いつつ、個人情報や頻繁に変わるデータをGit履歴へ入れず、権限・バックアップ・容量・保持期間をデータ種別ごとに管理するためです。

## Q-R2: 元画像と配信用画像

WebP/AVIFは画質を保ちながら容量を減らせますが、非可逆圧縮では元データと情報量が完全に同一ではありません。画面サイズで見たときに同等に感じる配信用画像は作れますが、将来の再編集、トリミング変更、大判印刷、再エンコードまで同等に行うには元データが必要です。

本プロジェクトでは次の二層を採用します。

- 元データ: 編集・再生成が必要な写真や図版だけを非公開オブジェクトストレージ（Cloudflare R2を第一候補）へ保存する。公開URLを直接与えず、運営者権限でのみ取得可能にする。
- 配信用: 表示幅に合わせた複数サイズのWebP/AVIFを生成し、公開サイトの静的アセットまたはR2の公開配信バケットから配る。PNG/JPEGは必要な互換用途に限定する。
- Git: 小規模なSVG、ロゴ、ソース管理すべき図だけを置き、大量の写真原本は置かない。

容量は実データ未提示のため概算です。1万枚の場合、原本を平均8〜20MBと仮定すると約80〜200GB、配信用を1枚あたり3サイズ・合計0.4〜1.5MBとすると約4〜15GBです。現在のリポジトリは配信用画像6ファイルで約1.3MBです。導入前に実画像100枚程度で変換試験し、画質基準と平均容量を測って再見積もりします。

## Q-L2: 新しいジャンル作成の現行フロー

現状、運営UIに「ジャンル作成」機能はありません。ジャンル（コード上はカテゴリ）は `src/content/subjects/*.yaml` の `categories` にslug、名称、順序、説明を追加し、必要なら `src/content/concepts/*.yaml` と `src/content/articles/` の原稿を追加して、PRの検証・レビュー・マージを経て公開します。記事編集画面のカテゴリ候補はこのコンテンツ定義から生成されます。したがって現状はリポジトリを編集できる担当者が作成者です。L-4で既存ジャンルの概要を運営画面から確認できる入口を追加しますが、分類体系の誤変更を防ぐため、今回のUIから直接ジャンルを作成する機能は追加しません。

## Q-E2: 複数人の同時編集

現状はリアルタイム同期を行っておらず、WebSocketや共同カーソルもありません。保存APIは更新時刻や版番号を条件にせず更新するため、同じ原稿を二人が開いて保存した場合は後から保存した内容が最終状態になります（後勝ち）。各保存前の内容は `editorial_document_revisions` に残りますが、自動マージや競合警告はありません。

コード確認箇所は `src/admin-worker.ts` の原稿更新処理と `src/pages/admin/editor.astro` の保存処理です。ローカルD1と管理Workerを起動し、同じ原稿へ独立したクライアントA・B相当のPATCHを順に送る試験を実施しました。両方とも200で保存され、最終本文は後から送ったB、版履歴は `A, initial` の順で残りました。したがって現在の仕様が「後勝ち＋各保存前の版を履歴保存」であることを実データで確認済みです。誤上書きを防ぐ本格対応は、`updated_at` を保存要求に含め、サーバー側の `UPDATE ... WHERE updated_at = ?` が0件なら409を返す楽観ロックが適切です。

## Q-CM4: コメント・返信の通知

コメントまたは返信が付くと、原稿の `created_by` と一致する作成者には通知ベルへ通知されます。自分自身が付けたコメントは通知対象外です。既読状態は `admin_notification_reads` に利用者ごとに保存されます。今回、既読後も内容を残すN-1の表示修正を行います。

## Q-CM5: メンション通知

現状の `@表示名` は入力候補と強調表示だけで、メンションされた本人専用の通知は生成していません。原稿作成者がメンションされた場合は通常のコメント通知として届きますが、作成者以外には届きません。今回、本人の登録表示名を含むコメント・返信を通知対象へ加えます。
