## 先に埋める受け入れ体制

担当者名や返信目標は未決定。運営責任者が実際の担当者と合意して埋める。空欄を自動で管理者1人へ割り当てない。

| 担当                        | 主担当         | 代理者         | 連絡方法 | 合意する目標             |
| --------------------------- | -------------- | -------------- | -------- | ------------------------ |
| 応募確認・結果の案内        | 未決定         | 未決定         | 未決定   | 初回返信の目安           |
| 初回ログイン・権限・Discord | 未決定         | 未決定         | 未決定   | 問合せへの返信目安       |
| 数学など担当分野のレビュー  | 分野ごとに決定 | 分野ごとに決定 | 未決定   | 初回フィードバックの目安 |
| 保存・通知・公開処理の障害  | 未決定         | 未決定         | 未決定   | 発見時の連絡と判断者     |
| 相談・休止・退会            | 未決定         | 未決定         | 未決定   | 引継ぎ確認の目安         |

相談が担当者本人についての場合に使える窓口も決める。参加者の共通案内には、既存の[お問い合わせ](https://atlasez.org/contact/)への導線を設ける。窓口の受信・対応者も開始前に確認する。

## 1人ごとの準備と初週

1. `/admin/applications/?project=atlas`で本人の応募・審査結果を確認する。採否は担当者の判断を記録し、参加準備のためだけに仮の採用状態へ変えない。
2. `/admin/permissions/?project=atlas`と`/admin/genre-roles/?project=atlas`で、合意した担当分野と執筆・フィードバックの役割を確認する。全体管理や公開担当の権限を初回参加者へ一律付与しない。メールアドレスを推測して登録しない。
3. 本人に、応募時のGoogleアカウントで`/applicant/`を開いて結果と初期設定を確認してもらう。基本情報・プロジェクト内自己紹介を保存したら、ポータルと`/admin/getting-started/`へ案内する。チュートリアルは任意。
4. 受入担当者、代理者、初回レビュー担当者、連絡先、無理のない作業量を本人と決める。Discord参加・連携・ロールと、必要な資料へのアクセスをそれぞれ確認する。未連携を原因不明のログイン失敗として扱わない。
5. 閲覧できる担当記事を1本選ぶ。タスクテンプレートの「初回タスクの作業例」で内容を入力し、記事URL・相談先・確認担当者を追記する。期限は本人と合意して設定する。保存しただけではタスクは作成されないので、「タスクを作成」後に本人のタスク一覧で確認する。
6. 初週は記事の読み手として具体的なコメントを1件まとめる。記事編集のフィードバック依頼を使う場合は、依頼先と対応タスクを確認する。公開操作を初回タスクの完了条件にしない。
7. 確認担当者が返答し、本人と完了条件を確認する。作業量・使いにくかった画面・相談しやすさを振り返り、次の小タスクを決める。停止中のタスクには理由と次に確認する人を残す。

## 初回タスクへ追記する項目

既存のタスクの内容・作業メモを使う。新たな会員情報の保管場所を作らない。

```text
対象記事URL：
取り組むこと：読み手として分かりやすかった点と確認したい点をコメントする
成果物：記事コメントと、確認担当者に共有したURL
完了条件：確認担当者の返答と、次の修正方針を確認できた
受入担当者／代理者：
確認担当者：
相談方法：
期限とタイムゾーン：本人と相談して設定
対象外：記事の公開、担当外原稿の取得、他人の権限変更
```

## 歓迎案内に含める情報

送信前に受入担当者が本人の状況に合わせて用意する。通知は重複させない。

- 参加プロジェクトと担当分野、応募時のGoogleアカウントを使うこと。
- [応募状況](https://admin.atlasez.org/applicant/)、[ポータル](https://admin.atlasez.org/admin/portal/)、[参加後の案内](https://admin.atlasez.org/admin/getting-started/)のURL。新しい案内は配信確認後に送る。
- 受入担当者・代理者・確認担当者の名前と連絡先。
- 最初のタスクURL、完了条件、相談した期限、次の相談予定。
- Discordや資料共有の手順。使えない場合の連絡方法。
- 不具合は時刻・タイムゾーン・URL・操作・エラー文を伝えること。パスワード・認証コード・Cookieや他人の個人情報は送らないこと。

## 受け入れ記録と終了判断

実際の応募・タスク・権限変更は既存画面と監査ログに残す。氏名・メール・スクリーンショットなどの個人情報をGitHubのPR/Issueやこの文書に転記しない。開発検証の記録はSHA・画面URL・役割・結果と秘密値を含まない証拠に限定する。

初回ログイン、担当記事の閲覧、コメント保存、相談への返答、初回タスク完了までを本人が実行できれば、初週の受け入れを完了として記録する。自動試験だけでは本人の体験、実メール到達、実Discord権限の確認を代替しない。
